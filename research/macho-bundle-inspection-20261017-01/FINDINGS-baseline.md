## Method

- `tool/gen_fixtures.py` writes 37 parse fixtures and 20 small bundle trees (plus decoys outside them) with real `mach_header_64` / `fat_header` / load command layouts. Generating twice gave identical trees (`baseline-*/04`, `05`); snapshot in `fixtures-parse/*.bin` and `fixtures-snapshot.tar`.
- `scripts/probe_stock_macholib.py` runs each stock entry point in a child Python (`-I`) with a 60 s wall timeout, `RLIMIT_AS` 1 GiB and `RLIMIT_CPU` 30 s.
- `scripts/run_otool_oracle.sh` runs `llvm-otool-18 -l` and `-L` on every regular fixture file.
- Table: `evidence/baseline-stock-macholib-*/baseline-summary.md` (generated by `scripts/summarize_baseline.py`). Raw data: `probe-results.jsonl`, `otool-oracle/*.log`.

## A. Raw parsing (`MachO`, `MachOHeader`) - defects for untrusted input

These matter for an inspector of untrusted bundles. They are not problems for macholib's main purpose (py2app on trusted build output).

| id | finding | fixtures |
|---|---|---|
| A1 | Accepts malformed load commands that llvm-otool rejects: `cmdsize` not a multiple of 8, `lc_str` offset past `cmdsize`, `lc_str` offset inside the fixed struct, string without NUL in the command. The parse "succeeds", so a caller can mistake it for a complete inventory. | m08, m10, m15, m11 |
| A2 | No fat table validation: a `fat_arch` cputype that does not match the slice header, and two slices of the same arch, are both accepted. | m21, m22 |
| A3 | One bad slice aborts the whole fat file (`MachO.load_fat` loops and raises), so the good slice and its identity are lost. Conservative (no false pass), but not a per-slice inventory. | u01, u02 |
| A4 | Unbounded memory from a small input: section data is read eagerly, and overlapping sections are read once each. A 320,368 byte file reached `MemoryError` at the 1 GiB `RLIMIT_AS` (max RSS 1,042,696 KiB). Without an outer bound this can kill a test worker. | m17 |
| A5 | Errors are untyped (`struct.error`, `ValueError`, `IOError`); some messages embed the file object repr, which includes the local path. | m01-m07, m09, ... |
| A6 | Strictness differences, not defects: `sizeofcmds` larger than the commands (m24), and the last command running past `sizeofcmds` (u01/u02 broken slice), are rejected by macholib but accepted by llvm-otool 18. dyld behaviour for these is not verified (no macOS here). | m24, u01, u02 |

What works: well-formed thin, fat and fat64 files parse; unknown commands raise by default (`allow_unknown_load_commands=True` keeps them as raw bytes); raw command bytes are kept in `commands[i][2]`; `LC_REGISTRY`, `LC_NAMES` and the struct layouts cover every command used here, including `LC_LAZY_LOAD_DYLIB`, `LC_LOAD_UPWARD_DYLIB` and `LC_DYLD_ENVIRONMENT`; targets are opened read-only (`"rb"`).

## B. Helpers with intentionally limited scope - unsuitable here

| id | finding | fixtures |
|---|---|---|
| B1 | `MachOHeader.walkRelocatables` / `_RELOCATABLE`: leaves out `LC_LAZY_LOAD_DYLIB`, includes `LC_PREBOUND_DYLIB` (not a load). Decodes with the filesystem encoding, so a non-UTF-8 path raises `UnicodeDecodeError`. `data[ofs:data.find(b"\0", ofs)]` silently drops the last byte when there is no NUL (`@rpath/libnonul-ab.dyli`); this one is a real helper bug (silent data loss). It does not report `LC_RPATH`. | t09, b19, t07, m11 |
| B2 | `python -m macholib dump`: dependency names only, deduplicated, no `LC_RPATH`, no per-slice status. Exit 0 for empty, short, script and Java-class files, which it skips silently (`is_platform_file`). Symlinks are skipped silently. The first exception prints a traceback and exits 1, and the remaining output is lost. | m01, m02, m04, m23, m18 |
| B3 | `dyld.dyld_find` / `MachOGraph`: no `@rpath` support at all. Every `@rpath` dependency becomes `MissingMachO`, even when it sits next to its loader. With `env=None` it reads 5 `DYLD_*` variables from `os.environ`; with `DYLD_LIBRARY_PATH` (explicit env dict or inherited environment) it opened and parsed decoy libraries outside the bundle. It probes host paths with `os.path.isfile` (absolute names and fallback dirs such as `~/lib`, `/usr/local/lib`). On macOS >= 10.16 it loads `libSystem` with `ctypes` and asks the host dyld shared cache. | b01, b02, b04, b06, b19 |

## Decision at this checkpoint (falsifiable)

1. **Rejected: stock macholib alone as the reader or resolver for an untrusted bundle check.** Reason: A1/A2 (false acceptance), A4 (unbounded memory), B1-B3. This is falsified if a pinned macholib release makes fixtures m08, m10, m11, m15, m21 and m22 raise, keeps m17 under a fixed memory bound with the same probe script, and adds `@rpath` handling that never reads the host environment or host paths.
2. **Resource bounds alone are not enough.** A timeout plus `RLIMIT_AS` turns A4 into a clean failure, and that is enough to keep the test worker alive. It does not stop A1/A2, where malformed commands parse "successfully" and could become a complete inventory.
3. **Smaller path that needs no new parser:** on macOS, run native `otool -arch <a> -l` and `otool -arch <a> -L` on each Mach-O in the copied bundle, under a timeout. Treat any "error:", "is not an object file" (for an expected Mach-O) or `cmd ?(` as not passing. Grep the `LC_RPATH` / `LC_*DYLIB` path bytes for forbidden roots, then run the relocated runtime test. This path still needs a small output parser. It is not available on stock Linux Cloud images (llvm-otool happens to be installed in this container).
4. **Candidate for the next step:** a narrowly bounded load-command validator and JSON inventory. It would do the structural checks llvm-otool does, bound section reads, keep raw bytes and per-slice identity, and use macholib's `LC_REGISTRY` / `MachOHeader` only as the command registry and as a second parse to compare against. Bundle resolution would be limited to the image's own `LC_RPATH`, `@loader_path` and `@executable_path` inside the bundle. Inherited `@rpath`, `LC_DYLD_ENVIRONMENT`, lazy-load semantics, cwd-relative and unknown `@` tokens would be reported as unsupported context (not passing), not modelled. No host lookup.

## Addendum, 2026-10-17 (documentation correction; nothing rerun)

Source review of `scripts/probe_stock_macholib.py` and `scripts/replay_otool.sh` at `1116d14`. These are limits of the code, not observed crashes or resource exhaustion. The measurements above are unchanged.

- **Decision 2, "enough to keep the test worker alive", is qualified.** It holds only as an observation of this run: the probe finished. For m17, the `strict` and `walk` children reported `MemoryError` (max RSS 1,042,696 and 1,042,704 KiB), and the `dump` child exited 1 ("lost sys.stderr"). It is not a bound on the whole worker:
  - `RLIMIT_AS` and `RLIMIT_CPU` are set in `preexec_fn` and apply to the child only.
  - `subprocess.run(capture_output=True)` collects the full child stdout and stderr in the parent and decodes them before the tail is cut (`[-4000:]`, `[-2000:]`). Parent memory for capture and decoding is not limited.
  - A `setrlimit` failure in `preexec_fn` would raise in the parent, and `run()` does not catch it.
  - On timeout, only the direct child is killed, and the partial output is still captured in full.
- **A4, "Without an outer bound this can kill a test worker":** the outer bound used here was per child, as above.
- **Decision 3:** rc 0, a successful parse, or the absence of "error:", "is not an object file" or `cmd ?(` does not establish validity of an untrusted binary. The caller reports a bounded 12-fixture macOS arm64 replay with Apple `otool-classic` and stock macholib 1.16.4 (m08's alignment defect accepted; m10/m15 rc 0 with invalid-name indications; m24 rc 0 with an inconsistent-size diagnostic; m21 printing an inner x86_64 header for an arm64 request). These are caller-reported, not measured in this session, and listed in `README.md`. That path is an inventory aid, not a validity check.
- **Decision 4** stays stopped. The 932-line draft is frozen and unqualified, and no tool discrepancy reopens it automatically.
- **Retained results:** the `l-arch-.*` files named above are now `loadcommands-arch-.*` (checkpoint 2 rename, bytes unchanged).
